# Constant-orientation Cartesian ZONE implementation

Date: 2026-11-13. This implements the first milestone in [the Cartesian blend design](2026-11-13_cartesian_blend_design.md) in `modelrobot_internal`. It is a browser-workcell rule, not a reconstruction of EASY-ROB's unknown numeric ZONE blend law. The existing `ZONE r` metres syntax and `ZONE 0` exact-stop default remain.

## Accepted pair and reference curve

Two consecutive `MOVEL`/`MOVEC` commands may share one bounded flyby when both have positive ZONE, no other command except ZONE lies between them, and their TCP orientations remain within $10^{-4}$ rad of a fixed reference. The smaller radius applies. WELD-active pairs, changing orientation, and a third consecutive requested Cartesian corner fail with source-line diagnostics (`ZONE_WELD_UNSUPPORTED`, `ZONE_ORIENTATION_UNSUPPORTED`, `ZONE_RUN_UNSUPPORTED`). PAUSE, GRAB, RELEASE, TOOL, ROBOT, and non-Cartesian commands remain stop barriers. The first release plans one pair atomically; it never silently blends just one corner of a longer positive-ZONE run.

The inbound line/circle is retained from its start to an entry cut, and the outbound line/circle from an exit cut to its end. A CIRC via point must remain outside the cuts. For the transition, `frontend/planning/cartesian-zone.js` builds a fifth-degree Bézier position curve with endpoint tangent and curvature matched to the retained references. Let the local travel coordinate have span $h=d_{\rm in}+d_{\rm out}$, and let $u\in[0,1]$ with $\xi=\xi_{\rm entry}+hu$. At each cut, the Bézier endpoint derivative is $hT$ and second derivative $h^2K$, where $T$ and $K$ are the original unit tangent and curvature vector. This makes the *declared TCP position reference* C2 in $\xi$. The original LIN/CIRC references are exact by construction outside the transition.

All six Bézier control points must be inside the waypoint ball of radius $r$. Convex-hull containment therefore certifies that the entire declared transition stays in the ball, including between samples. Positive chord projections of all control-polygon edges certify forward chord progress and reject loops/reversals. These are conservative sufficient tests; an otherwise safe curve can be rejected. An opposing near-reversal cusp also fails explicitly.

`frontend/planning/paths.js` now exposes tangent/curvature on LIN/CIRC paths and accepts an ordered `requiredFractions` list in `solveCartesianPath`. The composite path includes entry, logical boundary, exit, and any inbound/outbound CIRC via fraction. The near-uniform IK grid drops points too close to any required fraction, preserving the exact required point without nearly duplicate spline knots. Existing long-arc CIRC and via behavior remains.

## IK, timing, events, and limits

`frontend/program-plan.js` first plans the nominal inbound move to resolve the second command's frame-relative target at the nominal exact-stop configuration. It then plans the composite path from the true current state using seeded 6D IK and one time parameterization over the whole pair. The composite path has zero speed only at its outer program endpoints; the timed logical boundary must have nonzero speed. Segmentwise internal-stop fallback is forcibly disabled even if a caller requests it in timing options. The pair is validated while the collision scene still has its current attachment state, before a later GRAB/RELEASE/JOIN may mutate it.

The returned program has two `plans` whose times meet at the logical boundary, and a separate serializable `cartesianZoneBlends` record with entry/boundary/exit times, radius, maximum **sampled** TCP distance from the waypoint, nonzero speed fraction, and required fractions. The existing `zoneBlends` array remains PTP-only for the current UI label. The Worker snapshot and response shape need no new transport mechanism.

The geometric ball bound is continuous for the *declared reference*. Realized FK residual, joint velocity/acceleration limits, and collision states/edges are checked on the existing dense/adaptive samples. If IK or timing deviates, the planner retries with denser IK samples or smaller cuts, then returns `ZONE_INFEASIBLE` or `ZONE_COLLISION` on the active ZONE line. This is **not** a continuous certificate for arbitrary mesh collisions or joint bounds. The joint trajectory uses the existing cubic Hermite joint interpolant, which is C1 at internal knots, and `ProgramPlayer` linearly interpolates the returned positions between samples. No C2 playback claim is made.

## Verification and remaining scope

`node --test tests/planning.test.cjs tests/planning-cartesian-zone.test.cjs tests/program-cartesian-zone.test.cjs tests/planning-zone.test.cjs tests/program-zone.test.cjs` passes 31 focused cases. New tests cover LIN→LIN, LIN→CIRC, CIRC→LIN, CIRC→CIRC, long-arc via preservation, exact-stop and PAUSE behavior, changing-orientation/weld/three-move errors, an invalid second CIRC with its own source line, Worker equivalence, strict ROS nanosecond ordering, sampled TCP/velocity/acceleration bounds, a blend-only obstacle with source-line `ZONE_COLLISION`, and a later GRAB whose future attachment would invalidate the earlier corner if checked retrospectively.

Chromium visual proof and UI help/status updates are archived in [the browser integration note](2026-11-13_cartesian_zone_browser.md); an independent [review](2026-11-13_cartesian_zone_review.md) found no remaining blocker after two diagnostic and timing-override fixes. Changing-orientation Cartesian blends, overlapping runs of three or more positive-ZONE moves, weld-path blends, analytic continuous collision/limit certification, and exact spline playback remain outside this milestone.
