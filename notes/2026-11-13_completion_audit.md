## T-10 and other explicit limits

- T-10 remains pending by decision: signal-triggered robot planning from a changed scene, Python-like syntax, LIN/CIRC blends, closed-loop kinematics, external axes, and multi-robot control. The scene can contain multiple objects, but this release plans one active serial URDF robot.
- Subsequent work implemented a bounded PTP-only `ZONE` flyby (D-15/T-15), deterministic signal scheduler (D-16/T-16), typed concurrent-program browser lab (D-17/T-17), kinematic `MOVE_MODEL` motion of detached nonstatic SDF models (D-18/T-18), and a shared simulation clock for an already planned robot trajectory plus later device moves (D-19/T-19). The full `npm run build` and `npm test` suite passes 127/127 after these changes. The ZONE browser trace shows a 5.714 mm waypoint bypass with nonzero joint speed, but takes 3.84 s versus 2.65 s at `ZONE 0`; see [ZONE note](2026-11-13_zone_ptp_blend.md). The [device note](2026-11-13_device_motion.md) and [review](2026-11-13_device_motion_review.md) show the tray moving X = 0.20 → 0.3125 → 0.65 m across logical ticks. The [shared-clock note](2026-11-13_shared_clock_ui.md) and [review](2026-11-13_shared_clock_review.md) show a robot plan ending at 0.548 s, then signal-triggered tray movement with Pause/Step/Reset and ZIP reopen. Device motion before the robot finishes is rejected because the robot path was planned against the initial scene; a signal cannot yet start a new robot plan from a scene changed by a device.
- Collision checking uses explicit geometry and adaptively sampled paths, not a continuous swept-volume proof. The UI should retain the educational-simulator framing. Visible links without collision geometry and missing meshes are diagnosed before planning.
- Full-pose IK is the local damped least-squares solver, not the initially considered external package. The tests establish fixtures, residuals, limits, singular/unreachable diagnostics, and browser reachability, but do not establish performance across a broad industrial robot corpus.
- SDF import/export supports documented static/kinematic elements; dynamic physics, general frame semantics, and arbitrary SDF constructs are not simulated. Unsupported elements receive diagnostics.
- Project ZIP preserves SDF object world poses, assets, program, limits, robot independent-joint positions, and attachment relationships, including a child→parent→robot hierarchy. The browser mid-carry ZIP test verifies exact saved joint values and model world poses after reopen. A legacy ZIP without `robot-state.json` still loads at home q. ZIP does **not** preserve playback time, joint velocities/accelerations, or controller execution, so it is not a running-program checkpoint.
- Weld path samples are checked against the selected object's surface; JOIN checks proximity to both objects at the event point. A continuous shared seam, joint strength, and material fusion are not verified.

## Joint-state persistence review

The new optional `robot-state.json` is linked from the existing version-1 project manifest. Its shape check requires unique nonempty joint names and finite positions; URDF-aware preflight requires exactly the independent joints and checks direct and mimic-derived limits before replacing the current workcell. Restore applies independent q values after URDF load and before world-preserving object attachment, which preserves both robot configuration and carried-object world poses. The Chromium fixture also injects `slide_x=999` m and confirms import fails without changing the current scene. `node --test tests/project-bundle.test.cjs tests/project-robot-state.test.cjs tests/weld-join-fixture.test.cjs` passed 6/6. I found no blocker or unintended regression in this path. See [joint-state note](2026-11-13_project_joint_state.md).

The `WELD_ALREADY_JOINED` diagnostic was corrected to avoid suggesting a prohibited RELEASE command.
